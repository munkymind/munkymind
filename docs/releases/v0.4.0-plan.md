# v0.4.0 plan: the Review queue

**Theme:** nothing changes your library without your OK. AI tools can now *save* things to Munkymind, not only read from it, and every save waits in a Review queue until you approve it. When a save contradicts something your library already says, Munkymind points that out before you decide.

Everything else is deferred to v0.5 (see the end).

## What ships

| Piece | What it does |
|---|---|
| **Review queue** (`mm/review/queue.py`) | Proposed pages wait here as `pending` until approved, rejected or replaced (`superseded`). Approving writes the page and indexes it; rejecting changes nothing. One JSON file per proposal, per user |
| **Page-changed conflict** | Each proposal records the version of the page it was written against. If the page changed before you approve, approval stops and says so; you can replace it anyway or reject |
| **Capture** (`mm/review/capture.py`) | The MCP `capture` tool and `POST /capture`: an AI tool saves an idea, decision, preference or fact while you talk. Validated, rate-limited, screened for secrets and prompt injection (those are held back, never queued), then queued as a proposal |
| **Capture check** (`mm/review/check.py`) | "This looks like a change of mind": the statement is compared with the most relevant pages in your library, using the answer model you already configured. A contradiction is flagged on the proposal and told to the AI tool, so it can ask you while you're there. A failed or slow check never blocks a capture |
| **Review in the viewer** | A ✅ Review tab with a waiting count: the list, each proposal's diff and flags, Approve / Reject |
| **Review from the terminal** | `munkymind review list / show / approve / reject / reindex` |
| **`munkymind doctor`** | Review checks (below) |

## What changes to fit a self-hosted, multi-user library

- **Per-user stores, no fixed paths.** Proposals live in `$DATA_ROOT/users/<name>/review/`; approved pages are written to the user's own `context-repo/<domain>/` folder, which Munkymind owns. Your notes folder is mounted read-only and is never written to.
- **No separate distil step.** A capture becomes a proposal straight away (one short page per capture), instead of being collected and rewritten into pages elsewhere.
- **No keyed-facts ledger.** The capture check compares against your pages (retrieved the same way a question is), not against a separate store of facts.
- **Your model, your key.** The check uses the user's configured answer model (Anthropic, OpenAI or Ollama), not a fixed one.
- **Generic clients.** `source_client` is any short name (`claude.ai`, `chatgpt`, `cursor`, `my-script`), not a fixed list.
- **Switches are environment variables**, documented in `.env.example`: `MM_CAPTURE`, `MM_CAPTURE_CHECK`, `MM_REVIEW_UPLOADS`.

## Default choices (safer first, each one switchable)

| Question | Default | Switch |
|---|---|---|
| Do uploads (`POST /ingest/files`) go through Review? | **Yes.** Each uploaded file becomes a proposal | `MM_REVIEW_UPLOADS=off` restores v0.3.0 behaviour (indexed at once) |
| Does the notes-folder sync / `munkymind ingest` go through Review? | **No.** They are your own files, already reviewed by you; the folder stays the source of truth | none (by design) |
| Can a read-only key capture? | **No.** Capture and decisions need a read-write key; read-only keys and login-link browser sessions can see the queue but not change it | none |
| Is capture on? | **Yes** | `MM_CAPTURE=off` refuses every capture |
| Is the capture check on? | **Yes**, when a capture is a decision, preference or fact and the library has related pages | `MM_CAPTURE_CHECK=off` |
| Does approving a capture edit the note it contradicts? | **No.** It adds a new page that says what it replaces; the old note is yours to edit | none in v0.4 |
| Rate limits | 10 captures a minute and 200 a day, per user and client | none in v0.4 |

## Migration for v0.3.0 users

- **Existing pages are untouched.** No database migration: the SQLite schema and the vector store are unchanged. The `review/` folder is created the first time something is proposed.
- **Notes-folder sync and `munkymind ingest`** work exactly as before.
- **Uploads** (`POST /ingest/files`) used to be indexed at once. They now return `{"status": "queued", "proposals": [...]}` and wait in Review. Scripts that need the old behaviour set `MM_REVIEW_UPLOADS=off`, or approve with `POST /review/{id}`. Approved uploads are kept as files under `context-repo/`, so their text survives a re-index (before, an uploaded file's text existed only in the index).
- **MCP clients** see one new tool, `capture`. Existing tools are unchanged.
- **Hosted deployments** need no data migration; set `MM_REVIEW_UPLOADS=off` if anything automated posts to `/ingest/files`.

## The user-facing flow

1. You tell your AI tool something worth keeping ("I've moved the 10k to March"). It calls `capture`.
2. Munkymind validates and screens it, runs the capture check, and queues a proposal. The tool hears "Saved to Review" and, if it contradicts a page, "Heads up, this looks like a change of mind: your library says X (page); this changes it to Y."
3. Open **✅ Review** in the viewer (or `munkymind review list`). The proposal shows the new page, any flags and the diff.
4. **Approve:** the page is written to `context-repo/<domain>/` and indexed, so the next question finds it. **Reject:** nothing changes.
5. If the page changed after the proposal was made, approval stops with "this page changed": replace it anyway, or reject.

## `munkymind doctor`

- Capture on or off; the capture check on or off
- Uploads wait in Review, or go straight in
- Review queue: how many are waiting; a warning when the oldest has waited more than 14 days
- Captures held back as possible secrets or instructions (a warning with where to look)
- Approved pages that aren't indexed (a warning with `munkymind review reindex`)
- The review folder can't be written to (a failure with the fix)
